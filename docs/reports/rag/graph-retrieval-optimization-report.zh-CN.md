# 图谱检索链路优化实施报告

## 1. 文档目的

本文记录 E2（Graph Only）检索诊断发现的问题、两阶段优化前后的完整链路、实际代码改动、验证结果和后续复测方法，并为 E2/E3 完整 RAGAS 结果预留统一的数据验收口径。

本轮只优化查询时的图谱检索，不修改：

- 既有知识库文档、标准 Chunk、实体、关系和来源绑定数据；
- E1～E4 已冻结的回答与 RAGAS 评分；
- `output/graph-diagnostics/e2-current` 优化前基线；
- 图谱构建模型及既有图谱版本。

因此本轮不需要执行数据库迁移，也不需要重新图谱化。是否需要局部重建图谱，应在优化后仍存在 A/B 类问题时再判断。

## 2. 优化前基线

基线来源：

`ragas-evaluation/output/graph-diagnostics/e2-current`

诊断集由 55 道已知异常题和 10 道正常控制题组成，共 65 题。基线采集 65/65 成功。

| 指标 | 优化前 |

### 2.1 问题最初如何暴露

问题不是通过阅读代码直接发现的，而是从第一轮 E1～E3 对照实验中暴露出来的。

实验条件分别为：

| 实验 | 检索方式 | 预期作用 |
|---|---|---|
| E1 | Vector Only | 单文档事实和语义相似问题的基线 |
| E2 | Graph Only | 实体关系、跨文档和多跳问题 |
| E3 | Vector + Graph | 使用向量召回补充图谱关系召回 |

按照设计预期，E2即使增加图遍历和实体提取耗时，也应该在关系型问题上获得质量收益；E3至少不应因为加入图谱分支而明显弱于E1。

第一轮汇总却出现了三个反常信号：

1. E2检索耗时明显高于E1。
2. E2部分问题的来源覆盖、Context Recall和最终答案质量低于向量检索。
3. E3虽然有向量检索兜底，但加入图谱后增加了明显延迟，质量收益与额外成本不匹配。

这些现象只能证明“包含图谱的链路存在问题”，不能直接证明是图谱构建错误。错误仍可能发生在：

```text
图谱构建
  → 查询实体提取
  → 实体锚点匹配
  → 图关系遍历
  → 图元素来源Chunk解析
  → 候选排序和去重
  → Top5与Token预算截断
  → 回答模型使用上下文
```

因此形成了两个相互竞争的假设：

- 假设H1：图谱中缺少正确实体、关系或来源绑定，需要重新图谱化。
- 假设H2：图谱已经找到正确候选，但查询阶段的来源解析、排序或Top5截断丢失了有效证据。

后续65题实验的目标不是直接提高最终答案分数，而是判断H1与H2中哪一个是主要矛盾。

### 2.2 为什么必须把检索和回答拆开

如果继续只看最终答案，无法区分以下情况：

- 图谱没有相关实体；
- 实体存在，但查询实体没有匹配；
- 已匹配实体，但图遍历没有经过正确关系；
- 已遍历正确关系，但关系没有绑定正确来源Chunk；
- 正确Chunk已进入候选池，但最终Top5没有选择；
- 正确Chunk已经进入上下文，但回答模型没有正确使用。

为隔离这些变量，诊断实验使用 `retrieval_only=true`：

```text
固定问题与标准来源
  → 只执行后端检索
  → 保存候选、选择结果、Graph Trace和耗时
  → 不生成答案
  → 不调用RAGAS裁判
```

这样排除了回答模型、回答Prompt和评测模型的随机性。65题结果只评价“标准证据在哪一步丢失”，不是最终回答质量。

### 2.3 65题诊断集如何组成

诊断集共65题：

- 55道异常题：来自第一轮E2/E3结果中出现来源未命中、来源覆盖不完整、Context指标异常或最终回答明显异常的题目；
- 10道正常控制题：来自原链路能够稳定命中全部标准来源的题目。

加入控制题有两个目的：

1. 防止只针对失败题调整规则，造成对诊断集的局部过拟合；
2. 验证修复异常题时，原本正常的检索能力没有被破坏。

诊断期间固定以下主要条件：

- 同一121题测试集及其标准来源标注；
- 同一个400 Token分块知识库；
- 同一份图谱实体、关系和来源绑定；
- 同一图谱构建模型及图谱版本；
- Graph Only检索模式；
- 相同的 `retrieveMaxResults`、`graphHopDepth` 和上下文预算；
- 不调用回答模型；
- 不运行RAGAS。

因此优化前后差异主要来自查询链路代码，而不是重新分块、重新向量化或重新图谱化。

### 2.4 为诊断增加了哪些可观测数据

每道题保存四个层级的数据：

| 层级 | 主要字段 | 用途 |
|---|---|---|
| 实体提取 | `directMatchedEntities`、`llmExtractedEntities`、`entityExtractionMode`、`entityExtractionParsedCount` | 判断问题文本是否找到图谱入口 |
| 图遍历 | `matchedAnchors`、`traversedEdges`、`hopDepth` | 判断是否经过正确实体和关系 |
| 来源解析 | `sourceCandidateSegmentUuids`、`resolvedSourceSegmentUuids` | 判断图元素是否能解析到来源Chunk |
| 最终选择 | `candidates`、`selected`、`retrievedDocumentNames`、`timingMs` | 判断正确候选是否被排序、Top5或Token预算丢弃 |

诊断产物保存在：

```text
output/graph-diagnostics/e2-current/
  ├─ retrieval_traces.jsonl
  ├─ graph_diagnostic_per_sample.csv
  ├─ graph_diagnostic_summary.json
  └─ GRAPH_DIAGNOSTIC_REPORT.zh-CN.md
```

其中：

- `retrieval_traces.jsonl` 用于逐题还原完整检索链路；
- `graph_diagnostic_per_sample.csv` 用于查看每题分类；
- `graph_diagnostic_summary.json` 保存汇总和逐题结构化诊断；
- Markdown报告用于快速阅读总体结果。

这些Trace不记录问题正文、答案正文、模型原始响应、API Key或隐藏思维链。

### 2.5 A～E分类规则

每道题使用测试集标准来源 `source_documents` 与检索结果进行比较。

设：

- `R`：该题标准来源文档集合；
- `C`：图谱检索候选池中的来源文档集合；
- `S`：最终进入回答上下文的来源文档集合。

分类规则为：

| 分类 | 判定条件 | 含义 | 优先排查位置 |
|---|---|---|---|
| A | 图谱没有有效入口或没有有效检索结果 | 图谱空结果 | 实体提取、别名、锚点匹配 |
| B | `R ∩ C = ∅` | 候选池没有标准来源 | 图遍历、关系来源绑定、来源Chunk解析 |
| C | `R ∩ C ≠ ∅` 且 `R ∩ S = ∅` | 候选池有正确来源，但最终选择丢失 | 排序、去重、Top5和Token预算 |
| D | `R ∩ S ≠ ∅` 且 `R ⊄ S` | 多来源问题只覆盖部分标准来源 | 多跳深度、来源多样性 |
| E | `R ⊆ S` | 全部标准来源进入最终上下文 | 检索链路通过 |

该分类把“没找到”和“找到了但没选中”分开。没有这个区分，C类问题很容易被误判为图谱实体或关系缺失，从而错误地要求重新图谱化。

### 2.6 65题结果如何分析

优化前65题结果：

| 分类 | 数量 | 占65题比例 | 数据含义 |
|---|---:|---:|---|
| A | 6 | 9.23% | 没有形成有效图谱结果 |
| B | 4 | 6.15% | 有检索过程，但候选池没有标准来源 |
| C | 35 | 53.85% | 已找到标准来源，但在最终选择阶段丢失 |
| D | 10 | 15.38% | 最终只覆盖部分标准来源 |
| E | 10 | 15.38% | 全部标准来源进入最终上下文 |

从这些原始数量可以得到三个关键比例：

1. 候选池任一标准来源命中为55/65，即84.62%。
2. 最终选择任一标准来源命中为20/65，即30.77%。
3. 在已经命中候选池的55题中，有35题在最终选择阶段完全丢失，占63.64%。

第三个比例最关键。它说明超过六成的“候选池已命中题”不是因为图谱里没有正确知识，而是因为候选组织和最终选择没有把正确证据送给回答模型。

按问题发生位置进一步合并：

- 入口或候选召回问题：A+B，共10题，占15.38%；
- 最终排序完全丢失：C，共35题，占53.85%；
- 多来源覆盖不足：D，共10题，占15.38%；
- 完整通过：E，共10题，占15.38%。

因此H2得到主要数据支持：查询阶段的排序和证据选择是最大故障点；H1只可能解释A/B中的部分问题，不应在这一阶段直接重新图谱化全部文档。

### 2.7 Trace如何把统计异常定位到代码

#### 2.7.1 实体提取链路

65题的 `llm_entity_count` 全部为0，但多数题仍产生了较长的图谱检索耗时。逐题Trace进一步显示：

- 59题已经通过问题文本直接匹配到实体；
- 系统仍然无条件调用LLM；
- LLM调用没有带来可解析的新增实体；
- 旧解析依赖严格分隔符，并存在正则分隔符误用。

由此定位出“已有直接实体仍调用LLM”和“非空响应可能解析为0”两个独立问题。这解释了图谱链路9～18秒的额外等待，也解释了部分A类问题。

#### 2.7.2 候选拼装与Top5

35道C类题的共同特征是：

- 标准来源已经出现在候选池；
- 正确关系或Chunk经常位于第6～8位；
- 最终只保留前5条。

检查候选构造代码发现，关系与原始Chunk没有在同一个相关性空间排序，而是按内容类型固定追加。数据中的“35道C类”与代码中的“第6～8位关系固定被Top5截断”形成了直接对应。

#### 2.7.3 来源池和跨文档覆盖

10道D类题的共同特征是：

- 已命中至少一个标准来源；
- 第二或第三标准来源没有进入最终上下文；
- 单个高连接度实体或同一文档的多个Chunk可能占满有限来源名额。

由此定位出来源池等于最终TopN、单图元素可占满候选、缺少文档多样性三个问题。

### 2.8 为什么第一阶段之后还需要第二阶段

第一阶段65题复测大幅提高了“文档名命中率”，但三题回答级测试暴露了文档级诊断的边界：

- 某些关系绑定16～24篇来源文档；
- 标准文档名出现在长来源列表中，就会被统计为命中；
- 关系描述本身可能不包含回答所需事实；
- 真正包含事实的原始Chunk仍可能没有进入Top5。

`eval_doc01_03` 是关键反例：

- 来源元数据表面上包含标准文档；
- Context Recall为0；
- Answer Relevancy为0；
- Answer Accuracy为0.5。

因此第一阶段证明了“正确来源可以进入候选体系”，第二阶段继续解决“候选是否包含真正可回答的证据”。这也是后来引入统一排序、关系来源歧义惩罚、扩大来源Chunk池和E2原始Chunk配额的原因。

### 2.9 诊断实验结论

65题实验最终把一个模糊问题：

> 图谱检索又慢又不准确，是否需要重新图谱化？

转化为四个可验证的工程问题：

1. 实体提取LLM被无条件调用且解析没有生效；
2. 正确候选大量存在，但被固定拼装顺序和Top5截断；
3. 来源池过小，高连接度元素挤占来源名额；
4. 多来源关系的文档元数据可能制造“命中但无有效证据”的假阳性。

所以本轮首先优化查询链路，而没有重新构建图谱或迁移数据库。只有优化后仍为A/B类、并确认实体、关系或来源绑定确实缺失的题目，才需要局部重新图谱化。

### 2.10 优化前查询链路

```text
用户问题
  ├─ 扫描图谱顶点，按实体名称直接包含匹配
  ├─ 无条件调用 LLM，要求输出旧式分隔符记录
  │    └─ 使用正则 split("<|>") 解析
  ├─ 合并直接实体与 LLM 实体，取 Top N 锚点
  ├─ 遍历一至两跳关系
  ├─ 解析来源
  │    ├─ 先查关系来源
  │    ├─ 再查实体来源
  │    └─ 第一批来源记录最多直接取 5 个
  ├─ 候选拼装
  │    ├─ 第 1～5 位：原始来源 Chunk
  │    └─ 第 6～8 位：图谱关系描述
  └─ Graph Only 最终 Top5
       └─ 第 6～8 位关系描述被固定截断
```

### 2.11 已确认根因

1. 65 题的 `llm_entity_count` 全部为 0。旧解析器既依赖严格输出格式，又把 `<|>` 直接作为正则表达式执行 `split`，因此模型返回非空时也可能静默解析为 0。
2. 59 题已经有直接实体，仍无条件调用 LLM，产生了没有召回收益的网络延迟。
3. 原始 Chunk 固定排在关系描述之前，Graph Only 的 Top5 结构性截掉第 6～8 位关系候选，直接形成 35 道 C 类问题。
4. 来源解析池等于最终来源数量，且单个高连接度实体可能占满来源名额，没有给后续问题相关性排序留下候选空间。
5. 多文档问题缺少前置来源配额，同一文档的多个候选可能挤掉其他标准文档。

## 3. 第一阶段设计原则

- 复用现有 `GraphStoreContentRetriever`、来源表和 `DeduplicatingContentRetriever`，不引入新的检索框架。
- 直接实体匹配成功时不调用 LLM；只有完全没有直接锚点时才执行 LLM 回退。
- 查询实体只抽取实体名称，不在查询阶段重复构造实体关系图。
- JSON 为主格式，旧格式仅作为兼容回退。
- 先扩大有界来源池，再在内存中按问题相关性和文档多样性选择最终来源。
- 原始 Chunk 与关系描述在进入 TopN 前统一组织，关系证据不再固定排在所有 Chunk 后面。
- 不记录模型原始输出、问题正文、答案、API Key或隐藏思维链。

## 4. 第一阶段优化后链路

```text
用户问题
  ├─ 扫描当前知识库图谱顶点
  ├─ 直接实体名称匹配
  │    ├─ 命中：直接使用，跳过 LLM
  │    └─ 未命中：调用 LLM 实体回退
  │         ├─ 要求 {"entities":[{"name":"..."}]}
  │         ├─ 兼容 JSON / Markdown 包裹 JSON
  │         └─ JSON失败时兼容旧分隔符格式
  ├─ 匹配图谱锚点并遍历关系
  ├─ 解析来源候选池
  │    ├─ 限定当前 kbUuid（元数据可用时）
  │    ├─ 关系来源优先，实体来源补充
  │    ├─ 来源池扩大到最终数量的 3 倍
  │    └─ 每个图元素最多贡献 2 个来源，抑制高连接度实体
  ├─ 来源 Chunk 按问题字符二元组相关性排序
  ├─ 每个文档优先最多保留 2 条，空位再软回填
  ├─ 关系描述和原始 Chunk 分别排序后交错合并
  └─ 交给现有 RRF / Rerank / Token预算 / TopN 打包
```

## 5. 第一阶段实施内容

### 5.1 查询实体提取

文件：

- `GraphExtractPrompt.java`
- `GraphQueryEntityParser.java`
- `GraphStoreContentRetriever.java`

改动：

1. 新增查询专用 JSON Prompt，只提取实体名称。
2. 直接锚点存在时设置 `entityExtractionMode=direct_only` 并跳过 LLM。
3. 无直接锚点时设置 `entityExtractionMode=llm_fallback`。
4. JSON 解析支持：
   - `entities` 对象数组；
   - `entities` 字符串数组；
   - `name`、`entity_name`、`entityName`；
   - Markdown 代码块包裹。
5. 保留旧分隔符格式兼容，并使用 `Pattern.quote("<|>")` 避免正则误解析。
6. Trace 只记录状态：
   - `entityExtractionMode`
   - `entityExtractionFormat`
   - `entityExtractionResponseNonBlank`
   - `entityExtractionParsedCount`
   - `entityExtractionErrorType`

这些字段不会保存 LLM 原始响应。

### 5.2 来源 Chunk 精确度

文件：

- `KnowledgeBaseGraphElementSourceService.java`
- `GraphStoreContentRetriever.java`

改动：

1. 保留原方法兼容现有调用，新增带 `kbUuid` 和每元素上限的重载方法。
2. 元数据可解析出知识库 UUID 时，对来源记录增加知识库过滤。
3. 来源池由最多 5 条扩大为最多 `maxResults × 3` 条。
4. 每个关系或实体最多贡献 2 个来源 Chunk。
5. 仍保持关系来源优先、实体来源补充。
6. 加载来源正文后，按问题与正文的字符二元组命中数量排序，再压缩回 `maxResults`。
7. Trace 分开记录：
   - `sourceCandidateSegmentUuids`：排序前来源池；
   - `resolvedSourceSegmentUuids`：最终入选来源。

### 5.3 关系候选与原文候选

文件：

- `GraphStoreContentRetriever.java`

改动：

1. 关系描述与来源 Chunk 分别按问题相关性排序。
2. 按“关系、Chunk、关系、Chunk”交错合并。
3. 最终交给现有 `DeduplicatingContentRetriever` 进行去重、RRF、可选 Rerank、Token预算和TopN打包。
4. 删除“先放满5个Chunk，再追加3条关系”的固定顺序。

该改动确保 Graph Only 的 Top5 中可以出现图谱关系证据，同时保留原始 Chunk 作为可核验依据。

### 5.4 跨文档覆盖

来源候选排序和图谱候选组织阶段均使用软性每文档上限 2：

- 有其他文档候选时，优先保留不同来源；
- 候选不足时允许回填同一文档，不会因为多样性规则导致上下文为空；
- 不修改最终 Token 上限和图谱描述 Token 比例。

## 6. 自动化验证

### 6.1 新增测试

`GraphQueryEntityParserTest`：

## 10. 第二阶段：关系与原始 Chunk 统一排序

### 10.1 触发原因

第一阶段纯检索诊断显著改善了文档命中率，但回答级三题烟雾测试暴露出新的结构性问题：

1. 图谱关系按内容类型固定进入 Top5，而不是与原始 Chunk 比较相关性。
2. 某些关系绑定了 16～24 个来源文档，只要列表中包含标准文档名，就会在文档级诊断中被误判为高质量命中。
3. E2 没有重排模型，关系描述占位后，真正包含完整事实的原始 Chunk 可能被排除在最终上下文之外。
4. 原 `eval_doc01_03` 虽然候选元数据包含标准来源，但最终回答的 Context Recall 和 Answer Relevancy 均为 0，证明“来源名命中”不能替代“证据内容有效”。

### 10.2 优化后的检索链路

优化前：

`实体匹配 → 图遍历 → 关系 Top3 → 关系/Chunk 固定交错 → Top5 截断`

优化后：

`实体匹配 → 图遍历 → 扩大来源 Chunk 池 → 关系与 Chunk 统一计算问题相关性 → 多来源关系歧义惩罚 → 文档多样性选择 → E2 原始 Chunk 配额保护 → Top5 截断`

具体规则：

1. 关系描述与原始 Chunk 进入同一候选列表，使用相同的词法相关性函数排序，不再按内容类型固定追加。
2. 原始 Chunk 获得小幅证据类型加分，因为它能向回答模型提供完整语境；该加分不会阻止高相关、来源精确的关系进入 Top5。
3. 关系绑定来源文档数超过 4 时，标记为 `graph_provenance_ambiguous`，并按来源数量施加惩罚。
4. 歧义关系不再携带可用于“文档命中”的精确 `kb_item_uuid/source_document_ids`，避免仅凭长来源列表制造假阳性；关系来源数量仍通过 `graph_source_document_count` 保留用于诊断。
5. 无重排的 E2 在原始候选充足时，Top5 至少保留 4 个原始 Chunk；关系只有在统一排序后足够相关且来源足够精确时才能占用剩余位置。
6. 图谱来源 Chunk 初始池由 `maxResults × 3` 扩为 `maxResults × 12`，每个图元素最多读取 12 条来源，使统一排序能够看到原先排在第 6～8 位之后的正确 Chunk。
7. 最终仍执行文档多样性约束，防止 Top5 被同一文档的重复片段占满。

这并没有把 E2 退化成普通向量检索：原始 Chunk 仍由图谱入口实体、关系遍历及图元素来源绑定产生；改变的是证据展示顺序，而不是检索入口。

## 11. 两阶段图谱检索链路总对比

为避免把第一阶段和第二阶段混为一次改动，下面按实际演进顺序汇总三条链路。

| 环节 | 原始链路 | 第一阶段优化 | 第二阶段最终链路 |
|---|---|---|---|
| 查询实体提取 | 无条件调用 LLM，依赖旧分隔符格式 | 直接实体命中时跳过 LLM；未命中时使用 JSON 回退并兼容旧格式 | 沿用第一阶段，不再增加额外 LLM 调用 |
| 图谱入口 | 直接实体与解析结果合并 | 保留直接锚点，增加可观测 Trace | 沿用第一阶段 |
| 图遍历 | 按锚点遍历一至两跳 | 保留源实体、关系和目标实体的相关性信号 | 沿用第一阶段，避免只按关系描述重排造成回归 |
| 来源解析 | 关系来源优先，来源池接近最终 TopN | 来源池扩大到 `maxResults × 3`，每个图元素最多贡献2条 | 来源池扩大到 `maxResults × 12`，每个图元素最多读取12条，再统一排序 |
| 候选组织 | 原始 Chunk 固定在前，关系固定追加到第6～8位 | Chunk 与关系分别排序后交错 | Chunk 与关系进入同一列表，以统一相关性分数排序 |
| 关系来源可信度 | 多来源关系携带全部来源，容易产生文档命中假阳性 | 尚未区分精确关系与高歧义关系 | 来源文档数超过4时标记歧义并惩罚，不再冒充精确文档证据 |
| Graph Only Top5 | 只按固定顺序截断 | 允许关系进入Top5 | 原始Chunk充足时至少保留4条，精确且高相关关系最多竞争剩余位置 |
| 跨文档覆盖 | 无来源多样性策略 | 每文档软上限2，候选不足时回填 | 沿用多样性策略，并在更大的来源池上执行 |
| 可观测性 | 无法区分实体提取失败、图遍历失败和来源丢失 | 增加实体、锚点、边、来源池及最终来源 Trace | 增加关系来源数量与歧义状态，能够识别“来源名命中但正文无效” |

### 11.1 原始链路

```text
问题
  → 无条件LLM实体提取
  → 旧格式解析
  → 图遍历
  → 最多读取少量来源Chunk
  → Chunk固定在前、关系固定追加
  → Top5截断
  → 回答模型
```

主要故障是：LLM调用慢且解析经常为0、候选池过小、内容类型决定候选位置、多来源关系制造假命中。

### 11.2 第一阶段链路

```text
问题
  → 直接实体优先 / JSON LLM回退
  → 图遍历
  → 有界扩大来源池
  → Chunk相关性排序与文档多样性
  → 关系和Chunk交错
  → Top5
  → 回答模型
```

第一阶段解决了实体解析、无效LLM调用、来源池过小以及关系固定落在第6～8位的问题。在65题诊断集上，最终选择文档命中率由30.77%提高到90.77%，但三题回答测试进一步证明，“关系进入Top5”本身不等于“关系应该优先进入Top5”。

### 11.3 第二阶段最终链路

```text
问题
  → 直接实体优先 / 必要时JSON LLM回退
  → 保留实体、关系、目标实体相关性的图遍历
  → 扩大图元素来源Chunk池
  → Chunk与关系统一计算问题相关性
  → 对多来源歧义关系降权并取消精确来源身份
  → 文档多样性选择
  → E2保护至少4条原始Chunk
  → Top5 / Token预算
  → 回答模型
```

第二阶段没有绕开图谱：原始 Chunk 仍由图谱锚点、关系遍历和图元素来源绑定召回。它修正的是“图谱检索到证据以后，如何把真正可供回答的证据送进上下文”。

4. 两组不可回答题仍保持6/6正确拒答，当前没有观察到为了提高召回而破坏拒答边界。
5. 这些数据足以证明检索链路和工程性能改善，但尚不足以给出“最终答案准确率提升多少”的完整结论。

### 14.4 量化结论

完整结果支持以下结论：

1. 图谱检索优化对E2产生了大幅且稳定的正向作用。Context Precision、Context Recall、Answer Relevancy、Answer Accuracy和Overall的95%置信区间均完全高于0。
2. 图谱检索优化对E3产生了幅度较小但可验证的正向作用。Context Precision和Overall获得稳定提升，同时检索P95下降76.1%。
3. E2与E3的收益幅度差异符合系统结构：E2完全依赖图谱检索，E3已有向量召回兜底。
4. 本轮优化没有通过重新分块、重新向量化或重新图谱化获得收益，改进来自查询实体提取、来源解析、候选排序、来源歧义控制和最终证据组织。
5. 结果中仍存在单题退化，尤其应继续跟踪 `eval_doc08_02`、`eval_cross_revised_15` 等案例；总体提升不意味着所有问题都已解决。

可以用于项目总结的最终表述为：

> 在相同测试集、知识库、回答模型和评测口径下，图谱查询链路优化使Graph Only的Context Precision由0.4022提高到0.7572、Context Recall由0.4713提高到0.7955、Answer Accuracy由0.5546提高到0.8487，五指标Overall由0.5554提高到0.7949；Hybrid的Context Precision由0.7281提高到0.8060，Overall由0.8468提高到0.8705。与此同时，Graph Only与Hybrid的检索P95分别下降78.2%和76.1%。配对Bootstrap结果表明，E2的主要质量指标以及E3的Context Precision和Overall均获得稳定提升，证明本次图谱优化同时改善了检索质量、回答质量和工程性能。
