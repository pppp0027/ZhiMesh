# Database initialization and migration

The authoritative target schema is the result of the current Java entities, mappers, runtime vector-table creation, and migrations `001` through `036`. See the [Chinese schema guide](../../docs/database/schema.zh-CN.md) for the complete inventory.

For a fresh database, run `all_ddl.sql`, then `all_dml.sql`, and finally exactly one of `all_dml_cn.sql` or `all_dml_en.sql`; before starting the application, run `020_remove_logical_delete.sql` with `psql -v ON_ERROR_STOP=1`. The legacy snapshot remains compatible with older initialization paths, and migration `020` converts it to the authoritative physical-delete schema. Vector tables are created at runtime for the configured embedding model and are intentionally absent from the static DDL.

For an existing database, do not run the `all_*` snapshots. Apply numbered migrations in order. For migrations `004` and `033`, select exactly one matching language variant; then continue through `036`. Migration `020_remove_logical_delete.sql` is an irreversible, one-time physical-delete migration and must be run only after its stated backup and preflight requirements are met. Migration `026` adds the canonical-chunk-backed BM25 document/posting schema and does not use PostgreSQL full-text ranking. Migration `027` adds the per-item BM25 lifecycle fields used by both management UIs. Migration `028` adds answer-level BM25 provenance. Migrations `029` and `030` add versioned knowledge-base route profiles and built-in local embedding-model identity compatibility. Migration `031` removes deprecated model configuration columns. Migration `032` adds the user avatar path and randomly assigns an avatar from the bundled pool to existing users. Migration `033` adds nine common prompt templates to each existing user without overwriting same-title prompts. Migration `034` reconciles legacy workflow runs left in READY/DOING: failed child nodes prove failure, a successful explicit End or graph-leaf node proves success, and only unresolved rows older than 30 minutes are classified as interrupted. It also aligns interrupted child rows and adds the partial index used by runtime heartbeat recovery; WAITING_INPUT is preserved. Migration `035` widens provider model identities, enforces platform-qualified uniqueness, and adds persistent OpenRouter model-state and synchronization-audit tables. Migration `036` documents cooperative workflow cancellation states and adds indexes for lightweight run-history pagination and lazy node details. Then run `verify_schema.sql`. The verification script is read-only and reports missing required tables, columns, and indexes, deprecated model columns, and installed extensions.

For BM25 rollout, apply migrations `026`, `027`, and `028` before starting a build with `ZHIMESH_BM25_ENABLED=true`. Existing user knowledge bases must then be reindexed with `POST /knowledge-base/indexing/{uuid}?indexTypes=fulltext`; system knowledge-base items can be submitted through `POST /admin/kb/items/indexing-list` with `indexTypes=fulltext`. Until every item in a requested knowledge base has a current FULLTEXT build, online traffic deliberately continues with Vector/Graph only.

Use PostgreSQL 16 with pgvector for PostgreSQL vector search. Apache AGE is required only when PostgreSQL graph retrieval is selected; Neo4j can be configured instead. Always back up production data and rehearse migrations with `psql -v ON_ERROR_STOP=1`.
